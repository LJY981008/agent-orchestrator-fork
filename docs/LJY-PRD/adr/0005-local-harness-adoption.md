# LADO 5. Adopt the local agent setup into one LADO-managed location

Date: 2026-10-19
Status: Direction accepted by the owner (2026-10-19). Delivery decided with the step 7 design (2026-10-26), measured on Linux on 2026-10-26 with claude 2.1.283, codex 0.163.0 and claude-agent-acp 0.70.0, and built in step 7. Windows and macOS refuse adoption until step 9 measures delivery there; restore runs everywhere.

## Context

The developer already has a lot of agent setup on the machine: user-level and project-level CLAUDE.md and AGENTS.md, settings with hooks and permissions, skills, subagents, commands, plugins and MCP servers. It is spread over `~/.claude`, `~/.claude.json`, `~/.codex` and every repository. LADO rules would conflict with it, and managing it in many places is hard.

Facts at `55b02b848`:

- **No AO UI lists this setup.** Only a Chat-only skills list (`httpd/controllers/conversations_skills.go:16-40`) and live MCP status exist.
- **The computer's own login uses the real folders directly.** AO sets no config folder for it (`service/agentaccounts/service.go:898-900`), so the user's `~/.claude` and `~/.codex` load in every such session.
- **Claude `default` reads the user's file.** It passes no permission flag, so `~/.claude/settings.json` decides the mode (`adapters/agent/claudecode/claudecode.go:160-162`).
- **Account homes mirror the real folders.** They link `skills`, `plugins`, `agents`, `commands`, `output-styles`, `hooks` and top-level `*.md` from `~/.claude` (`adapters/agentaccount/claude.go:26-30,268-274`), and copy settings key by key without login keys (:32-41, :280-323). For Codex they link nearly everything in `~/.codex` except credentials (`adapters/agentaccount/codex.go:15-35,198-230`).
- **AO writes into the user's folders.** The account linker creates missing shared entries in the user's real folder, or moves the account's copy there (`adapters/agentaccount/share.go:35-38,62-76`). AO also writes workspace trust into `~/.claude.json` (`adapters/agent/claudecode/claudecode.go:236-252`).
- **AO adds its own layer.** Worktree hooks (`adapters/agent/claudecode/hooks.go:11-16`), Codex hook flags (`adapters/agent/codex/hooks.go:72-116`), an `ao` MCP server (`session_manager/chat_spawn.go:345-373`) and a system prompt.
- **Codex can report its own configuration.** The app-server offers `config/read` with layers and origins, plus `hooks/list` and `plugin/list`. AO does not use them yet (`adapters/chatdriver/codexappserver/codexproto/protocol.gen.go:53-99,1225-1277`).

## Decision

The owner chose a single management point: an adopted item is backed up, copied into LADO's managed home, and removed from where it was. From then on only sessions launched by this app use it.

- **What is adopted.** User-level Claude Code and Codex setup (HARNESS §9.1). As built: Claude Code's top-level `*.md`, `settings.json` keys, the entries of `skills/`, `agents/`, `commands/`, `output-styles/` and `hooks/`, and the user MCP servers of `~/.claude.json`; Codex's `AGENTS.md`, `AGENTS.override.md` and `[mcp_servers.<name>]` tables. The first decision also adopted untracked project files; step 7 does not (Consequences).
- **What is never adopted.** Credentials, login keys, session history, caches, organization-managed settings and repo-tracked files. As built, also `~/.claude/plugins` and Codex's `skills/`, `plugins/`, `prompts/` and `rules/` (Consequences).
- **Flow.** Scan → preview → preconditions (no running Claude or Codex holding the files) → human-presence approval ([0002](0002-human-presence-approval-channel.md)) → backup with a hashed manifest under `<state>/lado/backups/` → copy into `<state>/lado/harness/` → remove the originals (only adopted keys inside `settings.json` and `~/.claude.json`) → record and verify. As built, the preconditions also refuse an OS whose delivery was not measured, and any live AO session of the tool; the approval signs the preview's plan hash.
- **Delivery to sessions**, as decided with the step 7 design (owner's design A, 2026-10-26) and built:
  - **Claude Code: a config home per session.** Once a managed Claude Code item is live, every Claude Code session AO launches, on an account or on the computer's own login, gets `<state>/lado/homes/<session-id>/claude/`. It links the state entries of the session's own folder (the account home or the real Claude folder), merges that folder's item entries with the managed items, and adds the managed settings keys and MCP servers to copies of its `settings.json` and `.claude.json`. `CLAUDE_CONFIG_DIR` points at the home.
  - **The login stays where it lives**, through `CLAUDE_SECURESTORAGE_CONFIG_DIR`: the account home for an account session, as AO already sets it, and for the computer's own login the daemon's `CLAUDE_CONFIG_DIR` when set, else the real Claude folder on Linux and Windows and `""` on macOS (the Keychain item without a suffix). Linking the credentials file does not work: Claude Code rewrites it through a temp file and a rename, refuses a symlink, and refuses a file with more than one hard link.
  - **Codex: launch options on the real `CODEX_HOME`.** Codex keys its login to `CODEX_HOME` (`auth.json`, a keyring entry named by a hash of the folder, or on Windows an encrypted file whose passphrase Credential Manager keeps under that hash), and nothing moves it apart, so a home of its own would lose the login. Adopted MCP servers reach the terminal as `-c mcp_servers.<name>=<inline table>` and Chat through the app-server thread config; adopted `AGENTS.md` or `AGENTS.override.md` text becomes a section of AO's system prompt.
  - **Account homes and AO's linker stay as they are.** Adoption keeps the item folders in the user's Claude folder and empties them, so the linker has nothing to create there. The first decision had the linker read from the managed home instead.
  - **Which versions.** An execution gets the item versions its rule snapshot pinned; every other session the current versions that are on for its project. Homes and options are built from stored versions only, never from the managed folder.
  - Launch options for Claude Code, the planned fallback, were not needed.
  - An item kind is adoptable only if it reaches both the TUI and the Chat path of its tool. That leaves Codex with instructions and MCP servers.
- **Changes.** Every change to a managed item shows a diff and needs approval. Changes that can run code or widen access need human presence. Versions are kept as blobs. Repo-tracked files change only through git, for example a task with a prefilled plan.
- **Drift and restore.** Items that reappear at original locations are offered for adoption, never moved automatically. Restore writes the backup back byte for byte and never overwrites something newer.

## Consequences

- Claude Code and Codex used directly, including IDE extensions, no longer see adopted items. That is the intended effect. Restore is the way back.
- LADO edits the upstream account linker (`adapters/agentaccount/share.go`) and adds a launch-home hook. Both are small hooks under D1. As built, the linker is not edited; the hooks are in the session manager (the top of `prepareWorkspace` and the Chat controller callbacks), the Codex adapter's launch and restore commands, the Chat MCP lists, and `pkg/agentcreds`, which reads Claude Code's login through `CLAUDE_SECURESTORAGE_CONFIG_DIR` as Claude does (TDD §1.2).
- Removing or restoring files under the user's tool folders happens only on an explicit, approved request. LADO's own copies, backups and manifests stay under `~/.ao`, as `AGENTS.md:120` requires.
- Each execution's setup home is built from immutable blobs, so running agents never see edits made after admission.
- Step 7 departs from the first decision in three places, each decided or approved by the owner on 2026-10-26:
  1. **`~/.claude/plugins` stays where it is.** It held 510 MB on the owner's machine and Claude Code writes it as it runs. Only the `enabledPlugins` and `extraKnownMarketplaces` settings keys are adopted, every config home links the plugin folder, and the rule snapshot hashes the install records of the enabled plugins, so an update shows on approved tasks.
  2. **Untracked project files are not adopted.** `CLAUDE.local.md` and `.claude/settings.local.json` in a project's main checkout are listed read-only: AO's worktrees never contain them, so adopting them would change direct use without serving any AO session, and writing them into worktrees risks committing personal files.
  3. **Repo-tracked files are not hashed into the rule snapshot.** They reach a worker through its worktree and the base branch, whose movement step 6 records instead of refusing; the scan reads the main checkout, which can differ from that branch. Their Edit opens a New Task for the project.
- Measured on Linux on 2026-10-26 (`service/ladosetup/probe`): with claude 2.1.283, `CLAUDE_CONFIG_DIR` at a lab home and `CLAUDE_SECURESTORAGE_CONFIG_DIR` at the real folder keep the login, and without the second variable the same home is logged out; the home's instructions, settings hook, skill, agent, command and MCP server load in print mode, and the ACP adapter (claude-agent-acp 0.70.0) lists the home's command and skill; the transcript lands in the real `projects/` through the link, and no credentials file appears in the home. With codex 0.163.0, a `-c` server is in the `sessionFlags` layer of `config/read` and a `config.toml` table in `user`.
- Still to verify, in step 9: the same on Windows and macOS. Build the ACP runtime (`npm --prefix frontend run build:acp-runtime`), then run `AO_LADO_SETUP_PROBE=1 AO_LADO_SETUP_PROBE_CODEX=<codex binary> go test -count=1 -v -timeout 15m -run '^TestDeliveryProbe' ./internal/service/ladosetup/probe/` in `backend/`, which runs `TestDeliveryProbeClaudeTUI`, `TestDeliveryProbeClaudeChat` and `TestDeliveryProbeCodex`; without the variable they skip. On Windows, check symlinks (Developer Mode), the probe hook's `touch` (Git Bash) and the codex path first; the probe already uses the empty value on macOS. An OS where the three pass becomes verified in `domain.LadoSetupDeliveryVerified` and its test; until then adoption answers `LADO_SETUP_OS_UNVERIFIED` there.
